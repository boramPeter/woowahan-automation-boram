# 실시간 주문 현황 화면의 테스트 자동화 전략

## 1. 자동화 전략

### 1-1. 무엇을 자동화하고 무엇을 수동으로 둘까

**방향성: 기간이 2주라서 "개발하면서 자동화구현"으로 진행 필요함.**

이번 스프린트에서 자동화는 개발이 끝난 뒤에 붙이는 게 아니라 개발과 같이 진행될 가능성이 높음. 그러면 화면과 흐름이 아직 바뀌고 있는 상태에서 테스트를 구현해야 하고 이 점이 레이어별 투자 규모를 정하는 가장 큰 기준으로 삼음.

- API는 설계를 먼저 진행한다. api 명세가 확정된 지점부터 바로 자동화를 구현. 
- UI는 로케이터와 화면이 바뀔 가능성이 높음. 유지보수가 많이 들기 때문에 상대적으로 적게 구현.
- E2E는 앱, 서버, 환경이 모두 엮여서 유지보수가 가장 큼. UI보다도 더 적게, 기본 flow 검증만 진행.
- 적게 만든 만큼 부족한 UI와 E2E 커버리지는 매뉴얼로 진행. 매뉴얼 테스트는 개발 완료가 되는 시점인 1주일 뒤로 가정해서 시작.

**판단 기준**

| 기준       | check point                   | 이번 기능에 적용하면                                         |
|----------|-------------------------------|-----------------------------------------------------|
| 변경 가능성   | 개발이 끝나기 전까지 얼마나 바뀔 것 같나       | API는 설계가 완료된 지점부터 자동화.                              |
| 안정성      | 같은 입력에 같은 결과가 나오는 멱등성         | 상태 값, 응답 필드, 권한은 보통 크게 달라지지 않음. 구현에                 |
| 실패 비용    | 고객에게 다가갈 Risk                 | 남의 주문 노출, 취소 상태 오표시는 치명적이라 매뉴얼로 더블 체크 필요            |
| 반복 횟수    | 2주 동안 몇 번 돌리나                 | PR마다 도는 API 검증은 이득이 큽니다. 오픈 직전 전체 리그레션은 매뉴얼 병행으로 진행 |
| 시간 대비 효과 | 자동화 구현 시간이 수동으로 대체되는 시간보다 작은가 | 아래 ROI로 체크                                          |

**자동화하는 것**

*API (설계 완료 시점부터 착수)*

- 정상 흐름: 접수 → 조리 → 픽업 → 배달 중 → 완료. 단계마다 상태, 예상 시각, 다음 행동 필드가 스펙대로 내려 오는지
- 예외: 취소, 가게 사정 취소, 지연, 존재하지 않는 주문, 이미 끝난 주문 재조회, 만료된 토큰, 진행 중 주문 0건
- 권한: 다른 회원의 주문 번호로 조회하면 거절되는지. 
- 갱신: 상태가 바뀐 뒤 다음 조회에 새 상태가 오고 이전 상태가 남지 않는지
- 동시성: 취소와 상태 갱신이 겹쳐도 최종 응답이 취소인지

*UI (대표 화면만, 적게)*

개발 중에 response를 모은뒤 mitmproxy로 개인정보와 토큰을 지운 fixture를 만들고, request를 캡쳐해서 response응답을 강제 주입해서 화면만 확인. 모든 상태를 다 만들지 않고 대표 화면별로만 검증한다.

- 진행 중 주문 없음, 조회 실패와 재시도
- 대표 상태 몇 가지의 단계 표시 (예: 접수, 배달 중, 취소)
- 취소 상태에서 진행 중 버튼이 사라지는지

문구 전체 일치나 세부 레이아웃은 넣지 않고 확정되면 그후에 추가한다.

*E2E (기본 flow만, 가장 적게)*

- 실시간 전체 주문 flow를 happy path기준으로만 검증한다.


**수동으로 두는 것**

- 자동화를 적게 한 만큼 비는 UI·E2E 커버리지: 나머지 상태별 화면, 진행 중 주문이 여러 건일 때의 선택, 취소 후 화면 흐름 등. 개발 완료 추정 시점(약 1주일 뒤)부터 수행.
- 시각 요소: 간격, 디자인요소, 모션, 지도 마커 이동 등
- 실기기 환경: OS별 푸시 권한, 백그라운드 복귀, 약한 네트워크
- 실제 배달 환경: 라이더 위치 지연, 경로 이탈, 장기 지연 문구

**변경사항과 flaky, bug를 분리해서 기록**

UI와 E2E는 개발 중에 깨지는 일이 자주 발생. 이때 실패의 원인을 구분하지 않으면 전부 수정에 필요한 리소스로 들어가게됨. 따라서 실패할 때마다 원인을 나눠서 기록하고, 나눈 결과에 따라 다르게 처리.

| 분류 | 이렇게 판단합니다                                      | 처리                                    |
| --- |------------------------------------------------|---------------------------------------|
| Flaky | 같은 빌드, 같은 데이터에서 실행할 때마다 간헐적으로 결과가 다름. 재실행하면 통과 | 자동화 판정에서 빼고 매뉴얼 확인 테스트로 전환. 원인은 따로 분석 |
| 로케이터·flow 변경 | 요소를 못 찾거나 화면 순서가 달라짐. 빌드 사이에 UI 변경 이력이 있음      | 유지보수 대상. 로케이터와 흐름을 수정. 매뉴얼 확인 진행 X    |
| 버그 | 같은 입력에서 항상 틀린 화면. 기획 의도와 다름                    | 버그 이슈로 자동 등록                          |

API도 같은 식으로 분리합니다. 실패 원인이 아래 셋 중 무엇인지 기준을 정함.

| 분류 | 이렇게 판단합니다 | 처리                            |
| --- | --- |-------------------------------|
| 버그 | 설계 문서와 응답이 다르고 항상 재현됨 | 버그 이슈로 자동 등록                  |
| 요구사항 변경 | 설계나 기획에 변경 이력이 있고, 응답은 새 스펙과 일치함 | 테스트의 기대값 수정. 변경 내용을 변경 이력에 기록 |
| Flaky | 같은 코드, 같은 입력에서 결과가 달라짐. 보통 테스트 데이터 공유나 타이밍이 원인 | 격리하고 원인 분석 (2-1-1 참고)         |

이렇게 나눠 기록하면 주 단위로 "이번 주 실패 중 버그가 몇 건이고, 변경 대응이 몇 건이고, flaky가 몇 건인지"를 볼 수 있습니다. 변경 대응이 크게 늘면 UI·E2E 자동화 범위를 더 줄이는 근거가 됩니다.

#### 1-1-1. UI / API / E2E 배분 (테스트 피라미드)

| 레이어      | 케이스 수 | 비중 | 확인하는 것 |
|----------| --- | --- | --- |
| API      | 25~40개 | 약 75~80% | 상태 전이, 예외, 권한, 갱신 |
| UI  | 5~8개 | 약 15~20% | 대표 상태의 화면 표시 |
| E2E      | 1~2개 | 약 5% 이하 | 진입, 새로고침 없는 갱신 |
| 수동       | 체크리스트 | 자동화 밖 | 자동화하지 않은 UI·E2E 범위, 시각, 실기기, 실제 배달 환경 |

비중은 목표치이고, 구현하면서 보정합니다. 이렇게 나눈 이유는 결함이 생기는 위치와 유지보수 비용이 레이어마다 다르기 때문입니다.

- 상태 값 오류, 권한 누락, 전이 규칙 오류는 API에서 가장 싸게 많이 잡힙니다
- UI는 개발 중에 가장 자주 깨지는 레이어입니다. 대표 화면만 두고, 나머지는 수동으로 보완합니다
- E2E는 한 번 만들고 유지하는 비용이 가장 큽니다. 실시간 갱신을 증명하는 데 필요한 기본 flow만 둡니다

일정은 아래처럼 잡았습니다.

| 시점 | 할 일                                                                                                               |
| --- |-------------------------------------------------------------------------------------------------------------------|
| 지금 ~ 1주차 | API 설계가 확정된 부분부터 자동화 착수. 상태별 응답 수집해 response set 준비. UI·E2E는 화면이 굳을 때까지 코드는 쓰지 않고, 개발자에게 요소 식별자를 요청해서 로케이터 변경을 줄임 |
| 개발 완료 추정 (약 1주일 뒤) | 대표 UI와 기본 E2E 자동화를 최소 범위로 작성. 같은 시점에 나머지 UI·E2E를 수동으로 시작                                                          |
| 2주차 | 수동 테스트 수행, 자동화 실행 결과 확인, 변경·flaky 분류 정리                                                                           |

#### 1-1-2. 자동화 ROI는 어떤 기준으로 판단할까

해당 내용은 ROI를 테스트 개수가 아니라 시간으로 하며, 기준은 세 가지.

1. **매뉴얼테스트 소요시간**: 수동으로 전체를 테스트할 경우를 2주로 설계. 요구사항분석 ·설계 리뷰와 테스트 설계 기간까지 포함한 시간.
2. **자동화 비용**: 자동화 구현 시간 + 유지보수 시간 + 자동화가 대체하지 못한 부분을 수동으로 수행하는 시간
3. **비교**: 두 시간을 비교하고, 시간이 비슷하다면 커버리지와 회귀 가능성으로 결론을 내어 어느부분이 이득인지를 최종판단.

아래 숫자는 근거 있는 실측이 아니라 판단 과정을 보여주기 위한 가정치이며, 실제로는 첫 주에 API 몇 개를 만들어 보면서 보정.

**수동으로 전체를 하는 경우 (단위: MH)**

| 항목 | 시간 |
| --- | --- |
| 요구사항·설계 리뷰와 테스트 설계 | 2 |
| API 수동 수행 | 3 |
| UI 수동 수행 | 3 |
| E2E 수동 수행 | 2 |
| 합계 (회귀 1회당 수행 8일이 추가됨) | 10 |

**자동화 방식 (이 전략)**

| 레이어 | 자동화 구현 | 유지보수 | 자동화가 대체하는 수동 1회분 | 못 대체해서 수동으로 남는 시간 |
| --- | --- | --- | --- | --- |
| API | 2.5 | 0.2 | 2.7 (커버리지 약 90%) | 0.3 |
| UI | 1.0 | 0.5 | 1.2 (약 40%) | 1.8 |
| E2E | 1.0 | 0.5 | 0.6 (약 30%) | 1.4 |
| 합계 | 4.5 | 1.2 | 4.5 | 3.5 |

설계 2일은 수동일 때와 같이 소요. 첫 회 기준 총 시간은 2 + 4.5 + 1.2 + 3.5 = 약 11.2일.

**회귀를 몇 번 돌리느냐로 비교하면**

자동화의 리그레션 1회 비용은 남은 수동 3.5일에 자동 실행과 결과 확인 약 0.3일을 더한 3.8일로 가정.

| 2주 안의 수행 횟수 | 수동 전체 | 자동화 방식 |
| --- | --- | --- |
| 1회 | 10일 | 약 11.2일 |
| 2회 | 18일 | 약 15일 |
| 3회 | 26일 | 약 18.8일 |

**레이어별 손익분기 (자동화가 몇 번째 실행에서 본전인가)**

손익분기 횟수 = (구현 + 유지보수) ÷ (대체하는 수동 1회분 − 자동 실행 0.1일)

| 레이어 | 손익분기 | 해석                                                              |
| --- | --- |-----------------------------------------------------------------|
| API | 약 1회 | PR마다 돌리므로 바로 이득. 가장 먼저, 가장 많이 투자                                |
| UI | 약 1.4회 | 개발 중 변경이 잦아 유지보수 변동이 커서 대표 화면 위주로만                              |
| E2E | 약 3회 | 수동 대체분이 작아 본전까지 가장 오래 걸림. 야간에 매일 돌릴 때 리소스 이득이 발생하므로 기본 flow만 유지 |

**결론**

- 시간은 첫 회에는 비슷하고(자동화가 약 1일 더 발생), 회귀를 2번 이상 돌리는 순간부터 자동화 방식이 이득을 보는구조. 2주 동안 회귀를 한 번만 돌리는 일은 현실적으로 없으므로 자동화 하는게 이득일 가능성이 높음.
- 커버리지로 보면 API는 전체의 약 90%를 PR마다 회귀하는 구조가 생김. 수동으로는 같은 횟수만큼 반복할 수 없음.
- UI와 E2E는 시간상 큰 이득이 없고 유지보수 위험이 큼. 따라서 약간의 이득은 포기하고 범위를 축소. 이 영역의 커버리지는 수동으로 확보
- 해당 판단은 첫 주에 실측한 구현 시간과 UI·E2E 변경 대응 시간이 가정보다 크면 범위를 더 줄이고, 작으면 늘리면서 유연하게 진행

## 2. 자동화 파이프라인 통합

### 2-1. CI/CD의 어느 단계에서 어떻게 실행하나

속도와 환경 의존도에 따라 세 단계로 분리. 기준은 하나이며. 머지를 막는 건 결과가 확실한 테스트만으로 한정.

| 단계 | 실행 | CI/CD 구분             | 트리거                         | 환경                                            | 막는 것 |
| --- | --- |----------------------|-----------------------------|-----------------------------------------------| --- |
| PR (merge 전) | API 전체 + UI 전체 | CI                   | PR 생성 / push                | 젠킨스, gihub action 같은 CI 도구 or n8n 같은 워크플로우 도구 | merge or 경고 |
| PR merge 후 배포 완료 | E2E 전체 | Argo 같은 CD (배포 후 검증) | merge → 테스트환경 배포 완료 | 자동화 수행 환경                                     | 없음 |
| D-1 전 | 위 전부 + E2E + 수동 체크리스트 | CD (릴리스 게이트)         | D-1 수동 실행 or 스케줄            | 스테이징 + 대표 기기 2종                               | 오픈 or issue raise |

**PR 단계**는 n분 안에 끝나는 것을 목표. 개발자가 2명뿐이라 피드백이 커밋 단위로 빨리 와야 하기 때문임. API 테스트는 처음부터, UI 테스트는 작성되는 시점(개발 완료 추정 이후)부터 게이트에 넣고 자동수행.  실패할경우 요청한 주문 상태, 기대한 값, 실제 응답등을 로그에 남게 해서 로그만 보고 원인파악을 할수 있게 구현해야함.

**통합 브랜치 야간**에는 E2E 수행. 실시간 갱신 시나리오는 여기서 매일 or 매시간 확인. 머지는 막지 않음. 결과는 flaky나 bug건으로 잡힌 것들 대상으로 수동 확인 후 개발자에게 공유하고, 결함으로 확인되면 그날 수정 대상으로 리포팅.

**D-1 전**은 한 번 수행. PR기반으로 다시 돌리고 E2E를 실행한 뒤, 수동 체크리스트(자동화하지 않은 UI·E2E 범위, 지도, 백그라운드 복귀, 약한 네트워크, 대표 기기 2종)등을 확인. 여기서 실패하면 raise 하거나 릴리즈를 홀딩함. 이 단계에서만 실패한다면 스테이징 데이터, 인증, 배포여부 등의 환경 차이를 먼저 분리해 보고, bug가 확정되면 수정 및 오픈여부를 논의.

테스트 데이터는 fixture(setup/teardown)로 제어. 테스트 본문은 데이터를 직접 만들거나 지우지 않고, fixture가 준비해 준 상태에서 테스트 수행.

scope은 session이나 module정도로 구현. 케이스에 따라 function등으로 축소가능 검토.

| fixture | setup                                                         | teardown                      | 범위 |
|---------|---------------------------------------------------------------|-------------------------------| --- |
| 계정·토큰   | 스테이징 전용 계정으로 로그인해 토큰 발급. 타인 계정, 만료 토큰 케이스용 fixture는 따로 분리     | 토큰 폐기                         | 세션 단위 (실행 1회에 한 번) |
| 주문 생성   | 테스트마다 새 주문 식별자로 주문 생성. 다른 테스트의 주문에 기대지 않음                     | 해당 주문만 취소·정리. 테스트가 실패해도 항상 실행 | 테스트 단위 |
| 상태 셋팅   | 상태 변경 hook(또는 어드민 API)으로 접수 → 원하는 상태까지 진행시켜 둠. | 별도 정리 없음 (주문 fixture가 함께 정리)  | 테스트 단위 |
| 저장 응답   | mitmproxy로 수집한 응답에서 토큰·전화번호 등을 제거한 마스킹본을 읽어 UI 테스트에 주입        | 주입한 response 해제               | 테스트 단위 |

- 토큰과 계정 정보는 코드나 저장소에 두지 않고, 실행 시점에 환경변수나 시크릿 저장소에서 읽거나 토큰을 그때그때 발급해서 관리.
- mitmproxy 원본은 커밋에서 제오. 마스킹은 수집 스크립트에서 자동으로 하고, response 세트만 repo에서 관리
- 정리(teardown)가 실패해서 남은 주문은 야간에 한 번 일괄 정리합니다. 잔여 데이터가 쌓이면 flaky의 원인 가능성 있음.

#### 2-1-1. Flaky 테스트가 생겼을 때

**재시도**

| 레이어 | 재시도 | 이유                                                |
| -- | --- |---------------------------------------------------|
| API | 하지 않음 | 간헐적으로 실패한다면 bug이거나 테스트끼리 상태를 공유되는 설계 미스일 가능성이 있음. |
| UI | 하지 않음 | 응답이 고정돼 있으니 같은 이유. 필요시 1회정도 retry 적용              |
| E2E | 같은 커밋에서 1회만 | 환경 영향이나 랜더링 성능이슈 고려 1회 retry 적용                   |

재시도로 통과해도 그 실행은 표시 필요. 리포트를 pass로만 남기면 flaky 모니터링이 어려움. 재시도 횟수는 테스트 코드마다 두지 않고 파이프라인 설정 한 곳에서만 관리하지만, 필요시 동적으로 적용하도록 param 구현 필요

**격리**

- 대상: 최근 3일 안에 원인 없는 실패가 2회 이상이거나, E2E가 재시도 후에 pass가 2회 이상인 케이스 (해당 기준은 예시. 수행하면서 유연하게 적용필요)
- 조치: PR 게이트와 릴리스 차단에서는 skip시켜 두고 매뉴얼로 원인파악 시작. 동시에 자동화 케이스는 매뉴얼 테스트로 전환해 커버리지 공백이 생기지 않게 함
- 담당자와 기한: 자동화 구현했던 담당자가 원인을 분석. 기한 기준은 약 1일. 기한 안에 분류가 안 되면 매뉴얼테스트 대상으로 내리고 자동화 집계에서는 skip.
- 격리 중에도 bug로 확인된 자동화 실패케이스는 개발 이슈로 열어 두고 skip 대상에서 제외.
- 복귀: 원인을 고친 뒤 CI나 CD환경에서 연속 10회 성공하면 게이트로 원복. 10회 안에 다시 재현되면 격리를(skip상태) 유지하고 원인 재분석

**원인 분석**

실패 원인은 아래 중 하나로 하고, 1-1에서 나눈 "버그 / 요구사항·로케이터·flow 변경 / flaky" 분류에 아래 두 가지를 더 세분화.

| 분류        | 증상                                             | 조치                            |
|-----------|------------------------------------------------|-------------------------------|
| bug       | 같은 입력에서 항상 잘못된 상태·권한·화면                        | 게이트에 두고 bug를 수정               |
| 변경·테스트 보정 | 기대결과가 스펙과 다름, 로케이터·flow가 바뀜, 이전 테스트 데이터가 남아 있음 | 수정 전까지 skip하고 수정 후 다시 자동화에 반영 |
| 타이밍 이슈    | 갱신되기 전에 기대결과를 확인함, 고정 sleep 사용                 | 수정 전까지 skip하고 수정 후 다시 자동화에 반영 |
| 환경 이슈     | 테스트환경 이슈, 인증 만료, 테스트 훅 실패 등                 | E2E에만 해당되며, 환경복구되면 재실행        |

실패했을 때 남기는 정보는 4가지.

1. 기대 결과와 실제 결과
2. 상태가 바뀐 시간과 고정 wait 시간
3. 스크린샷,실패로그 
4. UI·E2E는 실패한 순간의 화면 및 동영상
