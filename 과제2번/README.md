# B마트 재고 API 테스트 자동화

B마트 재고 API(조회 / 주문 / 취소)를 pytest로 검증하는 프로젝트입니다. 실제 서버가 없어서 Flask로 간단한 테스트 서버를 직접 만들었고, 테스트는 전부 비동기(`async`/`httpx`)로 작성했습니다. API 명세는 AI로 초안을 뽑은 뒤 제가 다듬었고, response 스펙은 [API_SPEC.md](API_SPEC.md)에 정리해 두었습니다.

## 실행

필요한 것은 [uv](https://docs.astral.sh/uv/) 하나입니다(없으면 `brew install uv`). 의존성(`flask`, `httpx`, `pytest`, `pytest-asyncio`)은 상위 폴더의 `pyproject.toml`에 있고, 처음 실행할 때 `uv run`이 가상환경을 만들어 자동으로 설치합니다. 그래서 `requirements.txt`나 별도 설치 명령은 없습니다.

받은 폴더의 `2번` 안에서 아래를 실행하면 됩니다. 러너(`runner.py`)가 테스트 서버 기동 → pytest 실행 → 서버 종료를 한 번에 하니 터미널 하나면 됩니다.

```bash
cd 과제2번 경로 (e.g., cd /Users/{user}/woowahan-automation-boram/과제2번 )
uv run python runner.py
```

옵션 (`2번` 폴더에서):
```bash
uv run python runner.py -m smoke               # 핵심 경로만
uv run python runner.py -m concurrency         # 동시성만
uv run python runner.py -m negative            # 네거티브(39~42)만
uv run python runner.py --case 14              # 시나리오(케이스 ID) 14번만
uv run python runner.py -k cancel -v           # 이름 필터 + 자세히
uv run python runner.py --base-url http://...  # 서버를 띄우지 않고 다른 서버를 대상으로 실행
```

`pytest`를 직접 실행하면 서버 주소를 알 수 없어서 "러너로 실행하세요"라는 메시지와 함께 종료됩니다.

## 테스트 서버

응답을 고정으로 내려주는 스텁이 아니라, 명세대로 동작하게 만든 간이 서버입니다. 동시성 테스트가 "먼저 온 요청은 성공, 나중 요청은 품절"을 확인해야 하는데, 이건 서버가 재고 상태를 가지고 있어야 가능하기 때문입니다.

- 재고는 `server/data/products.json`에 미리 만들어 둔 초기 데이터입니다. 상품 ID는 숫자 문자열입니다.
  - `100230451` 국산 생수 (재고 10)
  - `100871204` 한정판 딸기 케이크 (재고 1)
  - `100455890` 품절 상품 (재고 0)
- 서버가 뜰 때 이 파일을 임시 파일로 복사해서 DB처럼 읽고 씁니다. 원본 파일은 바뀌지 않습니다.
- 주문이 들어오면 JSON의 현재 재고를 읽어 판단합니다. 0이면 `SOLD_OUT`, 모자라면 `INSUFFICIENT_STOCK`, 충분하면 차감하고 저장합니다. 이 읽기→판단→쓰기를 락 하나로 묶어서, 동시에 들어와도 재고 숫자 기준으로 한 건씩 처리됩니다.

서버도 기대값도 제가 만든 거라 테스트가 통과한다는 건 "내가 정의한 명세와 내 서버가 일치한다"는 뜻이지 실서비스가 맞다는 뜻은 아닙니다. 그래서 `--base-url`로 실제 서버를 가리키면 같은 테스트를 그대로 돌릴 수 있게 해 두었습니다.

## 폴더 구조

```
runner.py              실행 진입점 (서버 기동 → pytest → 서버 종료)
pytest.ini             이 폴더 전용 pytest 설정 (마커, asyncio 모드)
server/
  app.py               Flask 테스트 서버 (엔드포인트, 락)
  db.py                JSON 파일을 DB처럼 쓰는 작은 클래스
  data/products.json   상품 초기 데이터
tests/
  api.py               비동기 API 클라이언트 + 상품 ID 등 상수
  asserts.py           검증 함수 모음 (assert는 여기에만 있음)
  conftest.py          fixture (데이터 준비 / 원복)
  test_stock_api.py    전체 42건 (표 기반 1~9 + 흐름/동시성 10~38 + 네거티브 39~42)
API_SPEC.md            API response 스펙
TEST_SCENARIOS.md      테스트 시나리오 1~42 (시나리오 N = 케이스 ID N)
```

## 테스트 구조

### 한 파일 안에서 두 방식을 씁니다 (`test_stock_api.py`)
- **표 기반 (케이스 1~9):** API가 4개뿐이라, 요청과 기대 응답만 보면 되는 에러 케이스(400/404/409)는 `parametrize` 표 한 곳에 모았습니다. 케이스를 추가하려면 표에 한 줄만 넣으면 됩니다. 재고가 그대로인지는 `normal_product` fixture의 teardown이 확인해 줍니다.
- **함수 (케이스 10~42):** "주문 → 재고 확인 → 취소 → 재고 확인"처럼 앞 응답을 다음 호출에 쓰는 시나리오와 동시성은 표로 쓸 수 없어서 함수로 썼습니다. 반복되는 동시성 9건(간격별 8건 + 10명 1건)만 `parametrize`로 묶었습니다.

### 케이스 ID
모든 케이스에 1~42 ID가 있습니다. 함수는 `test_c14_cancel_restores_stock`, 표/파라미터 케이스는 `c03_order_qty_zero`처럼 `cNN`으로 시작하고, 주석에 `# 케이스ID 14 | ...`(검증 내용)와 `# flow:`(진행 순서와 기대 결과)를 달았습니다. 이 ID는 [TEST_SCENARIOS.md](TEST_SCENARIOS.md)의 시나리오 번호와 같아서 `--case 14`로 바로 실행됩니다.

### 데이터 준비는 fixture로 (`conftest.py`)
테스트 본문은 준비된 상태에서 시작하고, 만들고 지우는 일은 fixture가 합니다. 재고를 다루는 fixture는 모두 function scope라 테스트마다 setup/teardown이 실행됩니다.

| fixture | 준비되는 상태 |
|---|---|
| `api` | 테스트마다 새 클라이언트. 이 클라이언트로 한 주문은 기록해 두었다가 teardown에서 전부 취소 |
| `normal_product` | 재고 10개 상품. setup: 재고 조회로 시작 값 기억 / teardown: 주문 원복 → 운영자 수정 복구 → 재고가 시작 값과 같은지 확인 |
| `last_product` | 재고 1개(마지막 1개) 상품. 위와 같은 원복 |
| `other_tab` | 같은 서버를 보는 다른 탭(별도 클라이언트). 조회 전용이라 원복할 주문 없음 (다른 탭 즉시 반영 케이스용) |
| `paid_order` | 재고 10개 상품에 2개가 이미 결제된 상태 (취소 시나리오용) |
| `sold_out_product` | cust-1이 마지막 1개를 결제해 이미 품절된 상태 (품절·재구매 시나리오용) |
| `base_url` | 러너가 넘겨준 주소(`BMART_BASE_URL`). 상태가 없어 session scope |

어떤 테스트가 재고를 어질러 놓으면 바로 다음 teardown의 재고 확인에서 드러납니다.

### 검증은 `asserts.py`에만
테스트 본문에는 `assert`를 직접 쓰지 않고 `assert_status`, `assert_stock`, `assert_order_paid`, `assert_one_winner` 같은 함수만 호출합니다. 기대값 형식이 바뀌면 이 파일만 고치면 되고, 실패 메시지도 한 곳에서 일관되게 관리됩니다.

### 마커
`smoke`(핵심 4건), `concurrency`(동시성 13건), `negative`(네거티브 4건) 세 개를 씁니다. 영역별 실행은 `-k`로 합니다.

### 네거티브 케이스 (39~42)
검증 함수가 틀린 값을 실제로 잡아내는지 확인합니다. 일부러 틀린 기대값을 넣고 `pytest.raises(AssertionError)`로 "실패가 났는지"를 보기 때문에, 실패가 나와야 PASS입니다. 예를 들어 39번은 재고 10에 11을 기대해 `재고 기대 11, 실제 10` 실패를 확인하고, 41번은 둘 다 201인 가짜 응답(과판매)을 만들어 동시성 검증이 이를 잡는지 확인합니다. 검증 함수가 항상 통과해 버리는 문제를 막는 용도입니다. 전체 실행(`uv run python runner.py`)에 기본으로 포함되고, `-m negative`로 이것만 따로 돌릴 수도 있습니다. (서버가 에러를 돌려주는지 보는 API 에러 케이스 1~9도 넓은 의미의 네거티브지만, 이쪽은 서버 응답이 아니라 검증 함수 자체를 확인합니다.)

### 재고 규칙 번호
문제의 재고 처리 규칙에 번호를 붙여 각 케이스 주석에 `[R2]`처럼 표시했습니다.

| 번호 | 규칙 |
|---|---|
| R1 | 장바구니 담기는 조회만, 재고 차감 없음 |
| R2 | 주문 결제 완료 시 수량만큼 즉시 차감 |
| R3 | 동시 주문 충돌 시 선착순, 이후 요청은 품절 |
| R4 | 주문 취소 시 재고 즉시 복구, 복구 후 바로 구매 가능 |
| R5 | 재고 0이면 품절 전환 (`soldOut`, `orderable`) |
| R6 | 운영자 수동 수정은 입력값으로 즉시 반영 |
| R7 | 수정 중 주문이 들어올 때의 처리 순서. 정의: 서버가 락으로 도착 순서대로 직렬 처리 (수정이 먼저면 새 재고 기준, 주문이 먼저면 이후 수정값으로 덮어씀) → 케이스 34~36 |
| R0 | 잘못된 입력, 없는 대상 등 공통 에러 응답 |

## 동시성 테스트

재고 1개 상품(`100871204`)에 A, B가 간격을 두고 결제합니다. 재고 1 확인 → 1건만 201(`remainingStock` 0), 나머지 409 `SOLD_OUT` → 재고 0 + 품절 응답까지 확인합니다. 간격은 `parametrize`(0~1000ms)로 넣고, 그 밖에 선착순과 10명 연달아 주문 케이스가 있습니다.

간격 실측 (목표 → 실제 발사 간격):

| 목표 | 0 | 5 | 10 | 20 | 50 | 100 | 500 | 1000 | 3000 |
|---|---|---|---|---|---|---|---|---|---|
| 실제(ms) | 1.5 | 5.3 | 10.9 | 21.0 | 51.1 | 101.1 | 501.4 | 1001.2 | 3001.3 |

3초까지 모두 1건 성공 + 1건 품절이었습니다. 다만 서버 처리가 약 3ms라 5ms 이상은 요청이 겹치지 않고, 락이 없어도 통과합니다. 락을 제거해 보면 0ms 케이스(22)와 수정·주문 동시(36), 큰 수량 동시(38)만 실패하고 나머지는 통과합니다.

## 아쉬운 점 / 앞으로

- 서버에 인위적인 지연이 없어서, 락을 빼면 과판매가 나는지까지는 확인하지 않았습니다. 지금 동시성 테스트는 락이 있는 서버가 불변식(성공 1건, 재고 0)을 지키는지만 봅니다.
- 락은 프로세스 안에서만 동작합니다. 실제 DB를 쓴다면 DB 쪽 락이나 조건부 UPDATE로 막아야 하는데, 이 환경에서는 검증할 수 없습니다.
- "다른 탭에 즉시 반영"은 화면/푸시 영역이라, 별도 클라이언트로 조회해도 바로 최신 값이 나오는지(케이스 32, 33)로 확인했습니다.
