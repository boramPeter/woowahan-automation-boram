# CI Flaky 원인 추적 순서 (원본 Kotlin 코드 기준)

원본은 실패해도 **예외와 스택트레이스만** 남습니다(스크린샷·로그 없음). 그래서 현재 구조에서 가능한 것부터 하고, 로케이터 상태를 볼 수 없으면 관찰용 계측을 추가합니다.

## 실패 지점 6곳

| 지점 | 대기 | 실패 증상 |
|---|---|---|
| ①~④ 치킨 / 후라이드 / 주문하기 / 결제 클릭 | 5s, 3s, 3s, 3s | 전부 같은 NPE (줄 번호로만 구분) |
| ⑤ `sleep(5000)` | 고정 | 실패 없음 |
| ⑥ "접수 대기" `assertNotNull` | 3s | `AssertionError` |

결제 후 "접수 대기"까지 허용 시간은 최대 8초(5s+3s)입니다.

## 추적 순서

### 1. 1차 필터링: 진짜 Flaky인가
**같은 커밋, 같은 케이스에서 pass와 fail이 섞이는지** 봅니다.

| 패턴 | 판정                     |
|---|------------------------|
| 같은 커밋·케이스에서 pass/fail 혼재 | Flaky → 2단계로           |
| 특정 커밋부터 계속 fail | 원인분석 (특정 커밋 및 로케이터 확인) |
| 같은 시각에 다른 테스트도 같이 fail | CI·서버 장애 (인프라 확인)      |

이때 실패율(예: 20회 중 3회)도 기록해 둡니다. 수정 후 비교 기준이 됩니다.

### 2. 트레이스로 실패 지점 특정
Flaky로 걸러진 fail들의 예외 종류(NPE / AssertionError)와 줄 번호를 모읍니다. 어느 지점에 몰리는지, 러너·시간대·앞 테스트와 겹치는지도 봅니다.

### 3. 그 지점 로케이터가 실패 순간 화면에 있었는지 확인
예외는 "못 찾았다"만 알려 줍니다. 원인은 실패 순간의 화면 상태로 갈립니다.

| 실패 시점의 화면 | 원인 |
|---|---|
| 다른 화면 / 팝업이 떠 있음 | 전환 지연, 앞 단계 오클릭, 팝업 |
| 로딩·처리중 화면 | 대기 시간 부족 (타이밍) |
| 비슷한 요소가 있으나 텍스트가 다름 | 문구 변경, 다국어 |
| 같은 문구 요소가 여러 개 | `textContains` 부분 일치로 엉뚱한 요소 선택 |
| 요소는 있는데 못 찾음 | 비활성, 화면 밖, 가려짐 |

현재 코드는 실패 시 화면을 남기지 않으므로, **실패 시 스크린샷과 hierarchy 저장(`TestWatcher`)을 추가해야** 이 확인이 됩니다(동작은 바꾸지 않는 관찰용). 재현이 되면 `adb shell uiautomator dump`로 직접 볼 수도 있습니다.
코드 수정이 불가능하다면, 육안으로 실제 동작되는걸 관찰하거나 별도로 녹화를 시도해야 합니다.

### 4. 가설 검증
변수를 한 번에 하나씩 바꿔 비교합니다: 같은 커밋 30~50회 반복, 러너 교차, 단독 vs 전체 스위트, 직렬 vs 병렬, `sleep(5000)`→`15000`.

- sleep 연장 시 ⑥ 실패가 사라지면 → 고정 대기가 응답 시간보다 짧음
- 연장해도 ⑥ 실패 → 결제 자체 실패 (서버·데이터)
- 단독 통과·스위트에서만 실패 → 앞 테스트 상태 오염

### 5. 수정과 재측정
고정 sleep → 조건 대기, null-safe 클릭 헬퍼, `resourceId` 정확 일치, 클릭 후 다음 화면 확인, `@Before`/`@After`로 초기화·정리. 1단계 실패율 기준으로 50회 이상 반복해 비교합니다.

## 주의
- ⑥ 실패는 **결제 이후**라 주문이 이미 나갔을 수 있습니다. 바로 재실행하면 중복 주문이 되고, 서버·PG 로그는 테스트 밖 권한이 필요합니다.
- 재시도는 환경 타임아웃에만 하고, 결제 이후에는 하지 않습니다.
