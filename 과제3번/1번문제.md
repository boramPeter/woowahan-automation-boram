# E2E 주문 플로우 테스트 코드 리뷰 (Kotlin + UIAutomator)

대상: `testOrderFlow()` — 가게(치킨) → 메뉴(후라이드) → 주문하기 → 결제 → "접수 대기" 확인

## 1. 안정성 (Flaky 요인)

| 문제 | 영향 |
|---|---|
| `wait(Until.findObject)` 결과를 null 체크 없이 `.click()` | 타임아웃 시 NPE. 어느 화면에서 실패했는지 알 수 없음 |
| `Thread.sleep(5000)` 고정 대기 | 느리면 실패, 빠르면 시간 낭비. 환경별 결과 불일치 |
| 근거 없는 대기 시간(5000/3000 혼재) | 느린 CI에서만 간헐 실패 |
| `textContains` 부분 일치 ("치킨", "후라이드", "결제") | 같은 문구가 여러 곳에 있으면 엉뚱한 요소 클릭 |
| 화면 전환 완료 대기 없음 | 이전 화면에 남은 요소를 잡거나 StaleObject 발생 |
| 팝업/권한/광고 대응 없음 | 이벤트·권한 팝업이 뜨면 흐름이 깨짐 |

## 2. 신뢰성

- **약한 단언**: `assertNotNull(statusText)` 하나뿐. 다른 화면·이전 주문의 "접수 대기"로도 통과. 메뉴명·금액·주문번호 미검증. 실패 메시지 없음.
- **상태 의존**: 로그인, 장바구니 초기 상태, 진입 화면을 보장하는 코드가 없음.
- **실제 결제 위험**: 운영 환경에서 진짜 결제·주문 발생. 테스트 계정/샌드박스 결제/주문 취소 정리 로직 없음.
- **데이터 오염**: `@Before`/`@After` 없음. 실패 시 장바구니·결제 중간 상태가 남아 다음 테스트에 영향.
- **중복 주문**: 결제 직후 실패 후 재시도하면 같은 주문이 또 생김(멱등성 없음).

## 3. 유지보수성

- 한글 텍스트 셀렉터 의존 → 문구 변경·다국어·A/B 테스트에 취약 (`resourceId`/testTag 필요)
- 문자열·타임아웃 하드코딩, `wait → click` 4회 중복
- Page Object 등 구조 없음 — 화면이 바뀌면 모든 테스트 수정
- 한 테스트에 전체 플로우를 몰아 넣어 실패 지점 파악·재사용이 어려움
- 테스트명 `testOrderFlow`가 검증 의도를 드러내지 않음

## 4. 관측성

- 실패 시 스크린샷, 화면 hierarchy 덤프, 단계별 로그 없음
- 단계별 소요 시간 미측정 → 성능 저하를 놓침

## 5. 누락된 시나리오

- 결제 실패/취소, 네트워크 끊김, 재고 없음, 영업 종료 가게
- 더블탭(중복 클릭), 백그라운드 복귀
- "접수 대기" 이후 상태 전이(접수 완료, 조리 중 등)

## 개선 방향

1. null-safe `waitAndClick` 헬퍼 + 타임아웃 상수화 (실패 시 못 찾은 요소를 메시지로 남김)
2. `Thread.sleep` 제거, 다음 화면 고유 요소가 뜰 때까지 조건 기반 대기
3. 텍스트 부분 일치 대신 `resourceId`/testTag 사용
4. 단언 강화 (주문번호·메뉴명·금액 확인, 실패 메시지 추가)
5. `@Before`에서 상태 초기화(로그인·장바구니 비우기), `@After`에서 주문 정리. 테스트 계정 + 샌드박스 결제 사용
6. Page Object 패턴으로 화면별 클래스 분리
7. 실패 시 스크린샷/hierarchy 자동 저장하는 `TestWatcher` Rule 추가
