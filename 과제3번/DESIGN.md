# 주문 플로우 E2E 리팩토링 — 구조와 설계 이유

원본(`original/`)은 Kotlin + UIAutomator, 리팩토링(`refactored/`)은 Python + uiautomator2 + pytest입니다. 실행 환경이 없어서 돌려보지는 못했고, 설계 의도가 드러나는 구조로 작성했습니다.

## 1. 한눈에 보기: 원본의 문제를 어떤 구조로 풀었나

원본은 한 함수 안에 "찾기, 기다리기, 클릭, 검증, 데이터"가 전부 섞여 있습니다. 문제가 한곳에서 생기지만 고치려면 전부 건드려야 하는 형태입니다. 그래서 **역할마다 파일(계층)을 나누고, 각 계층이 자기 책임의 문제만 풀도록** 했습니다.

| 원본의 문제 | 해결한 계층 | 이렇게 한 이유 |
|---|---|---|
| `wait()`가 null이어도 `click()` → NPE, 뭐가 안 보였는지 모름 | `base_page.py` | 찾기·대기를 한 곳에 모으면 "못 찾으면 이름이 담긴 예외"를 한 번만 구현해도 모든 동작에 적용됩니다 |
| `Thread.sleep(5000)` 고정 대기 | `base_page.py`, `pages.py` | 조건이 충족되는 즉시 넘어가야 느려도 안 깨지고 빨라도 안 낭비합니다 |
| `textContains("결제")` 같은 느슨한 셀렉터 | `pages.py` (로케이터) | 로케이터를 화면별로 모아 두면 "무엇을 누르는지"를 한눈에 검토하고 한 곳만 고칩니다 |
| 검증이 "접수 대기" 존재 여부 하나뿐 | `test_order_flow.py` (verify) | 무엇을 기대하는지는 테스트의 책임입니다. 상태·주문번호·가게·메뉴를 함께 봅니다 |
| 셀렉터·대기시간·데이터가 테스트 본문에 섞임 | 전체 분리 | 문구가 바뀌면 Page만, 시나리오가 늘면 데이터만 고치면 됩니다 |
| 결제 후 재시도하면 중복 주문 | `retry.py` | 재시도 정책을 테스트에서 떼어내 "무엇을 재시도하고 무엇을 하지 않는지"를 규칙으로 고정합니다 |
| 이전 테스트가 남긴 상태에 영향 | `conftest.py`, `session.py` | 매 테스트를 같은 출발점(앱 재시작)에서 시작해 순서 의존을 없앱니다 |

## 2. 구조

```
test_order_flow.py   시나리오(데이터)와 검증          ← "무엇을 기대하는가"
pages.py             화면별 Page Object              ← "각 화면에서 무엇을 할 수 있는가"
base_page.py         찾기/탭/대기 공통, 예외 타입     ← "어떻게 안전하게 다루는가"
retry.py             재시도 규칙                     ← "어떤 실패를 다시 시도하는가"
session.py           앱 재시작                         ← "깨끗한 출발점"
conftest.py          테스트마다 앱을 새로 띄우는 fixture
```

의존 방향은 한쪽으로만 흐릅니다.

```
test_order_flow ─→ pages ─→ base_page
        │                      ↑
        └──→ retry ─→ session, base_page(UiTimeoutError)
```

테스트는 "무엇을"만 말하고, Page는 "어느 화면에서 무엇을"만 알고, BasePage는 "어떻게"만 압니다. 아래층은 위층을 모릅니다. 그래서 앱 문구가 바뀌면 `pages.py`만, 대기 방식을 바꾸면 `base_page.py`만, 시나리오를 늘리면 테스트만 건드립니다.

## 3. 설계 결정과 이유

### 3-1. 화면마다 Page 클래스, 동작은 다음 화면 Page를 반환

`ShopPage → MenuPage → PaymentPage → OrderStatusPage` 순서이고, `select_shop()`은 `MenuPage`를, `order()`는 `PaymentPage`를 돌려줍니다. 테스트는 이렇게 읽힙니다.

```python
ShopPage(device).select_shop(...).select_menu(...).order().pay().read(...)
```

- **이유**: 화면 이동 순서가 코드 구조 자체에 들어가므로 테스트 본문이 시나리오처럼 읽히고, 순서가 뒤섞이는 실수가 줄어듭니다.
- **한계**: `PaymentPage(d)`처럼 직접 만들 수도 있어서 순서를 완전히 막지는 못합니다. "강제"라기보다 "자연스럽게 유도"합니다.

### 3-2. 화면 진입 확인용 `ANCHOR`

Page를 만드는 순간(`__init__`) 대표 요소가 보이는지 확인합니다.

- **이유**: 이게 없으면 화면이 안 넘어와도 다음 동작에서 엉뚱한 요소의 타임아웃으로 드러납니다. 있으면 "`MenuPage 화면 진입` 미노출"처럼 **어느 화면에서 막혔는지** 바로 나옵니다.
- **한계**: 시작 화면인 `ShopPage`는 대표 요소를 몰라서 `ANCHOR`가 없고, 이 확인도 없습니다.

### 3-3. 로케이터는 각 Page 맨 위에

- **이유**: 문구·ID가 바뀔 때 고칠 곳이 한눈에 보입니다. 원본처럼 코드 곳곳에 흩어져 있으면 놓치는 곳이 생깁니다.
- 원본의 `textContains("결제")`는 `{"text": "결제하기"}` 정확 일치로 좁혔습니다. "결제 수단" 같은 엉뚱한 요소를 누르지 않게 하려는 목적입니다.

### 3-4. 고정 sleep 대신 조건 대기 (`wait_until`)

- 결제 후에는 성공 화면과 실패 얼럿 중 **먼저 뜨는 쪽에서 즉시 반환**하고, 최대 30초만 기다립니다. 실패 얼럿을 먼저 확인합니다(성공 화면 요소가 함께 남아 있어도 실패를 놓치지 않도록).
- 30초는 서버 지연을 고려한 상한입니다. 조건이 충족되면 바로 통과하므로 길게 잡아도 평소엔 느려지지 않습니다.
- 주문상태 화면은 뜨자마자 읽으면 "결제 처리중"일 수 있어서, 상태 텍스트가 기대값이 될 때까지 기다린 뒤 읽습니다. 끝까지 안 바뀌면 타임아웃이 아니라 **"상태 불일치"** 검증 실패로 보고합니다.
- "성공 또는 실패" 같은 복합 조건은 uiautomator2의 단일 `wait`로 표현이 안 돼서 0.3초 간격 폴링을 썼습니다.

### 3-5. 실패를 두 종류로 구분: `UiTimeoutError` vs `AssertionError`

| 종류 | 의미 | 재시도 |
|---|---|---|
| `UiTimeoutError` | 요소·조건을 못 찾음 (환경 불안정일 수 있음) | 앱 재시작 후 1회 |
| `AssertionError` | 값 불일치, 결제 실패 (제품 결함일 수 있음) | 하지 않음 |

- **이유**: 환경 문제와 제품 결함을 구분하지 않고 전부 재시도하면 진짜 버그가 "재시도하니 통과"로 가려집니다. 타입을 나눠 두면 `retry`가 예외 타입만 보고 판단합니다.

### 3-6. 결제 이후에는 재시도하지 않음

- `pay()`가 결제 버튼을 누르기 **직전에** `device.payment_started`를 켜고, `retry`가 이 값이 켜진 실패는 다시 시도하지 않습니다.
- **이유**: 결제 후 실패는 주문이 이미 나갔을 수 있어서, 재시도하면 중복 주문이 생깁니다.
- 플래그를 누르기 직전에 켜는 건 "누르다 죽은 경우"도 안전한 쪽으로 처리하려는 선택입니다. 탭 자체가 실패해도 재시도되지 않는 부작용이 있지만, 중복 결제보다는 낫다고 봤습니다.

### 3-7. 검증은 모아서 한 번에 (`verify`)

- 상태·주문번호·가게·메뉴 중 틀린 항목을 **첫 번째에서 멈추지 않고 모아서** 보고합니다.
- **이유**: 첫 불일치에서 멈추면 나머지가 틀렸는지 알려고 한 번 더 돌려야 하는데, 이 테스트는 실결제라 반복 실행 비용이 큽니다.
- 검증은 테스트가, Page는 읽기만 합니다(`OrderSummary`는 읽은 값을 담는 객체). 기대값을 Page가 알면 Page를 다른 시나리오에서 쓸 수 없기 때문입니다.

### 3-8. 시나리오 데이터를 `OrderScenario`로 분리

- 가게·메뉴·기대 상태를 본문 밖으로 뺐습니다.
- **이유**: 시나리오 추가·파라미터화가 쉬워지고, 하드코딩이 본문에 섞이지 않습니다.

### 3-9. 매 테스트를 깨끗한 앱 상태에서 시작 (`conftest.py`)

- fixture가 매번 앱을 종료 후 재시작합니다. `retry`도 재시도 전에 같은 `restart_app`을 씁니다.
- **이유**: 이전 테스트가 남긴 화면·장바구니에 결과가 좌우되지 않게 합니다. 재시작 로직을 `session.py` 한 곳에 두어 두 곳이 같은 방식으로 복구합니다.

## 4. 한계와 가정 (그대로 쓰면 안 되는 부분)

- **가정값**: `APP_PACKAGE`(환경변수), resource-id(`order_status` 등), `주문하기`/`결제하기` 문구는 가정입니다. 실제 앱 값으로 교체해야 합니다.
- **선택과 검증의 기준이 다릅니다**: 가게·메뉴는 선택할 때 정확 일치, 검증할 때 부분 일치입니다. 실제 문구가 "OO치킨"처럼 길면 선택 단계에서 먼저 막힙니다.
- **정리 단계가 없습니다**: 테스트가 만든 주문을 취소하지 않아 실행할 때마다 주문이 쌓입니다. 실결제가 나가므로 테스트 계정이나 샌드박스 PG에서만 돌려야 합니다.
- **정상 결제 한 가지만 다룹니다**: 결제 실패, 네트워크 끊김, 재고 없음은 다루지 않았습니다. 금액·주문번호 형식도 화면 스펙을 몰라 검증하지 않았습니다.
- **언어가 다릅니다**: 원본은 Kotlin인데 이 리팩토링은 Python입니다. Kotlin이 필요하면 같은 계층 구조로 다시 옮겨야 합니다. 구조(Page 계층, 예외 구분, 재시도 규칙)는 언어와 무관하게 그대로 쓸 수 있습니다.
