# 설계

## 한 줄 요약

**기획서에서 기능분류트리를 만들고, 트리가 제대로 나왔는지 확인하고, 통과한 트리로 TC를 만들고, TC도 한 번 더 확인해서 문제 있는 것만 다시 만드는 QA 에이전트.**

TC를 LLM으로 만드는 일 자체는 어렵지 않습니다. 시간이 드는 건 나온 결과를 사람이 하나하나 검수하는 일입니다. 그래서 만드는 쪽보다 아래 두 가지에 공을 들였습니다.

- 요구사항을 바로 뽑지 않고 기능분류트리를 먼저 둡니다. 기능이 구조로 보이니까 "TC가 없는 기능"과 "기획서에 동작이 안 적힌 기능"을 찾을 수 있습니다. 트리가 틀리면 그 아래가 전부 틀어지기 때문에, TC를 만들기 전에 트리부터 확인합니다.
- 만든 결과를 확인합니다. 규칙으로 잡을 수 있는 건 규칙이 잡고, 뜻을 봐야 하는 것만 LLM이 판단하고, 고칠 수 있는 건 에이전트가 다시 만듭니다. 끝내 못 고친 것만 사람한테 갑니다.

## 풀려는 문제

| 문제 | 어떻게 막나 |
|---|---|
| 모델이 없는 기능을 지어냄 | 트리 노드마다 원문 인용을 받아서, 그 문장이 기획서에 있는지 글자로 대조합니다 |
| 기획서에 있는 기능을 트리가 빠뜨림 | 어느 노드의 인용에도 안 걸린 기획서 문장을 코드가 골라내고, 빠진 기능인지는 LLM이 판단합니다 |
| 기획서에 동작이 안 적힌 기능 | 추측으로 채우지 않고 "공백"으로 따로 빼서 기획 확인 요청으로 올립니다 |
| AC(인수조건)에 대응하는 TC가 없음 | TC마다 어떤 AC를 다루는지 적게 하고, 마지막에 TC가 없는 AC를 리포트에 올립니다 |
| 기대결과에 원문에 없는 값이 들어감 | 기대결과의 수치가 원문에 없으면 문제로 잡습니다 |
| TC 하나에 확인할 게 여러 개 | 스텝 길이와 "반복" 같은 표현을 규칙으로 막고, 프롬프트에서도 TC를 나누게 합니다 |
| 개수를 채우려고 쓸데없는 TC를 만듦 | 개수를 정해 주지 않고 "확인할 게 몇 개인지" 세게 합니다. 뺀 시나리오는 이유를 남깁니다 |
| 디자인 수치(px, 컬러값)가 TC에 섞임 | 금지 패턴으로 잡습니다 |
| 틀렸는데 결과가 멀쩡해 보임 | 못 고친 TC는 FAIL로 표시하고 이유를 비고에 적습니다 |

## 동작 구조

```
기획서
  │
  ▼
① 트리 생성  ⇄  ② 트리 검사      지어낸 기능 · 누락 · 모양
  │               문제가 있으면 피드백을 붙여 ①을 다시 (최대 2회)
  │ 통과
  ▼
③ TC 생성    ⇄  ④ TC 검사        규칙 → Judge, 지어낸 수치 · 분량 · TC 없는 AC
  │               문제 있는 TC만 ③을 다시 (최대 2회, 끝내 못 고치면 FAIL)
  ▼
리포트
```

| 단계 | 하는 일 | 코드 | 프롬프트 |
|---|---|---|---|
| ① 트리 생성 | 기획서의 기능을 대/중/소분류 트리로 정리합니다. 노드마다 원문 인용을 받습니다 | `tree.py` | `tree.md` |
| ② 트리 검사 | 지어냄, 누락, 모양을 봅니다. 문제가 있으면 피드백을 붙여 ①을 다시 하게 하고, 그래도 남으면 지어낸 노드는 잘라내고 누락은 리포트에 남깁니다 | `tree_check.py` | `tree_check.md` |
| ③ TC 생성 | leaf마다 AC와 힌트를 뽑습니다(동작이 없으면 공백). 요구사항 하나를 보고 TC 목록(서브젝트, 시나리오, 다루는 AC)을 먼저 짠 다음, 목록의 TC를 하나씩 사전조건·스텝·기대결과까지 채웁니다 | `tc.py` | `requirements.md`, `plan.md`, `write.md` |
| ④ TC 검사 | 규칙으로 먼저 거르고, 통과하면 LLM Judge가 봅니다. 문제 있는 TC에만 피드백을 붙여 ③을 다시 하게 합니다. 마지막에 어떤 TC도 다루지 않은 AC를 리포트에 올립니다 | `tc_check.py` | `judge.md` |

TC의 대/중/소분류는 따로 붙이지 않고 leaf의 경로를 그대로 가져옵니다. 그래서 같은 기능의 TC가 서로 다른 분류로 갈라지지 않습니다.

이미 분류 체계가 있다면 ①②를 건너뛰고 트리를 마크다운으로 직접 넣을 수 있습니다(`examples/sample_tree.md`). leaf 아래에 `AC:`를 적어 두면 ③에서도 AC를 새로 뽑지 않고 그 값을 씁니다. 직접 넣은 트리는 검사하지 않습니다.

## 이렇게 설계한 이유

- **트리를 먼저 둔 이유.** 요구사항을 바로 뽑으면 뽑힌 것만 보입니다. 빠진 기능은 목록에 없으니 빠졌는지도 알 수 없습니다. 트리가 있으면 leaf를 기준으로 비어 있는 곳이 보입니다.
- **트리를 TC보다 먼저 검사하는 이유.** 트리가 틀린 걸 TC를 다 만든 뒤에 알면 그 TC를 전부 버려야 합니다. 트리는 작아서 검사도 싸고 고치는 비용도 TC보다 훨씬 적게 듭니다.
- **만들기와 검사를 한 루프로 합친 이유.** 트리, AC, TC 모두 "만들고 → 검사하고 → 걸리면 피드백을 붙여 다시 만든다"는 같은 모양입니다. 이 루프를 `gate.py`에 한 번만 두면 재시도 한도(2회)와 "끝내 못 고치면 어떻게 하나"가 한 곳에서 정해지고, 단계마다 다른 건 무엇을 검사하느냐뿐입니다.
- **원문 인용을 요구한 이유.** 트리를 그럴듯하게 채우려고 기획서에 없는 기능을 지어내는 걸 막으려는 겁니다. 인용은 원문 그대로 복사하게 하고, 공백 차이만 무시한 채 기획서에서 찾습니다. 못 찾으면 피드백을 붙여 다시 만들게 하고, 그래도 남으면 그 노드를 하위 트리까지 통째로 잘라내고 리포트에 적습니다.
- **누락 검사를 "코드가 후보를 고르고 LLM이 판단"으로 나눈 이유.** 어떤 문장이 어느 노드의 인용에도 안 걸렸다는 건 코드가 정확히 압니다. 하지만 그 문장이 새 기능인지, 이미 있는 노드의 세부 설명인지는 뜻을 읽어야 압니다. 코드만 쓰면 세부 문장마다 누락 경보가 울리고, LLM만 쓰면 기획서 전체를 훑다가 감으로 판단해서 놓칩니다. 후보를 좁혀 주면 LLM은 문장 몇 개만 판단하면 됩니다. 후보가 없으면 LLM을 부르지 않고, 코드가 이미 큰 문제(지어낸 노드 등)를 찾았으면 그걸 먼저 고쳐야 해서 LLM 판단도 아낍니다.
- **공백을 따로 둔 이유.** 동작이 안 적힌 기능의 AC를 모델이 추측으로 채우는 게 가장 위험합니다. 공백은 QA가 기획서의 빈 곳을 찾아낸 결과이기도 합니다.
- **계획과 작성을 나눈 이유.** 한 번에 시키면 "빠진 게 없나"와 "문장을 어떻게 쓸까"가 한 호출 안에서 서로 방해합니다. 계획은 전체를 보고, 작성은 TC 하나에만 집중합니다.
- **다시 쓰는 건 실패한 TC만.** 전체를 다시 돌리면 멀쩡하던 TC까지 흔들립니다.
- **규칙을 Judge보다 먼저 돌립니다.** 규칙은 비용이 없고 결과가 항상 같습니다. 규칙에서 문제가 나오면 어차피 다시 쓰니까 Judge는 부르지 않습니다.
- **못 고친 건 FAIL로 남깁니다.** 버리지도, 통과시키지도 않습니다. 사람은 FAIL만 보면 됩니다.
- **LLM은 `complete(system, user) -> str` 하나만 알면 됩니다.** 어떤 모델을 쓸지 아직 정해지지 않아서 연결은 만들지 않았습니다.
- **노드 id(F1, F1.2 ...)는 코드가 붙입니다.** 모델이 준 id는 믿지 않습니다.

## 검사 설계

### ② 트리 검사 (`tree_check.check_tree`)

| 규칙 | 뜻 | 누가 | 심각도 |
|---|---|---|---|
| 원문 인용이 없음 / 인용이 기획서에 없음 | 지어낸 기능 | 코드 | major |
| 어느 노드의 인용에도 안 걸린 기획서 문장이 빠진 기능으로 판정됨 | 누락 | 코드가 후보를 고르고 LLM이 판단 | major |
| 3단계 초과 | 너무 깊음 | 코드 | major |
| 이름이 같은 형제 노드 | 중복 | 코드 | major |
| 이름이 없음 | 빈 노드 | 코드 | major |
| 자식이 1개뿐인 노드 | 단계를 하나 줄일 수 있음 | 코드 | minor |
| 누락 판단 응답이 깨짐 | 판단 못 함 | 코드 | minor (통과시키고 비고에 남김) |

누락 후보는 기획서를 문장 단위로 쪼개서(제목 줄 `#`은 뺍니다) 어느 노드의 인용에도 들어 있지 않은 문장입니다. LLM은 후보마다 "누락 / 포함됨 / 기능 아님" 중 하나로 답하고, 애매하면 "누락"으로 답하게 했습니다. 빠진 기능을 놓치는 쪽이 오탐보다 손해가 크다고 봤기 때문입니다. 누락이라는 답이 나오면 그 문장을 피드백으로 붙여 ①을 다시 하게 합니다.

### ③ AC (`tc.py`)

AC에 적힌 수치가 기획서에 없으면 피드백을 붙여 다시 뽑게 합니다. 두 번 다시 뽑아도 남으면 그 AC만 버립니다. 남는 AC가 하나도 없으면 그 leaf는 공백이 됩니다.

### ④ TC 규칙 검사 (`tc_check.check_rules`)

| 규칙 | 잡는 것 |
|---|---|
| 스텝이나 기대결과가 비어 있음 | 빈 필드 |
| 스텝 5줄 초과, 기대결과 3줄 초과 | 한 TC에 확인할 게 너무 많음 |
| 서브젝트 30자 초과 | 한눈에 안 읽힘 |
| `12px`, `#FF0000`, `node-id` | 디자인 스펙이 TC에 섞임 |
| "반복", "각각", "모두 확인" | 값마다 TC를 나눠야 한다는 신호 |
| 기대결과의 수치가 원문에 없음 | 지어낸 값 (환각) |

마지막 규칙이 제일 쓸모 있습니다. 환각은 "30분", "99.9%"처럼 그럴듯한 값으로 나오는데, 기대결과의 수치는 원문에서 가져온 것이어야 하니 글자 대조만으로 잡힙니다. 스텝에 적는 입력값은 테스트하는 사람이 정하는 것이라 대조하지 않습니다. AC 검사도 같은 함수를 씁니다.

### ④ LLM Judge (`tc_check.judge`)

TC 하나와 원문을 같이 보여 주고, 세 가지를 각각 PASS/FAIL로 답하게 합니다.

- 정확성: 원문과 어긋나거나 없는 내용을 지어내지 않았는가
- 완결성: 서브젝트가 말하는 걸 끝까지 확인하는가
- 명확성: 따로 해석하지 않고 그대로 따라 할 수 있는가

FAIL 이유는 다시 쓸 때 피드백으로 그대로 들어갑니다. Judge 응답이 깨져도 멈추지 않고 비고에만 남깁니다.

### 통과 기준 (`gate.run_gate`)

큰 문제(major)가 없으면 통과합니다. 있으면 피드백을 붙여 다시 만들고, 두 번 다시 만들어도 남으면 못 고친 것으로 봅니다. 못 고친 TC는 FAIL로 두고, 못 고친 트리는 지어낸 노드만 잘라내고 누락은 리포트에 남깁니다. 작은 문제(minor)는 비고에만 적습니다.

## 프롬프트 설계 (`tc_agent/prompts/`)

단계마다 프롬프트가 하나씩 있고, 본문은 `tc_agent/prompts/*.md` 파일로 코드와 분리해 뒀습니다(트리 생성, 트리 검사, leaf별 요구사항, 계획, 작성, Judge). 공통 원칙은 이렇습니다.

1. TC 개수는 우선순위가 아니라 "확인할 게 몇 개인지"로 정합니다.
2. TC 하나에는 확인할 것 하나만 둡니다. 값이 여러 개인 조건은 값마다 TC를 나눕니다.
3. 기대결과와 스텝에는 원문에 있는 동작과 수치만 씁니다. 모르면 쓰지 않습니다.
4. 뺀 시나리오는 이유를 적습니다.
5. 트리의 모든 노드는 원문 인용을 갖습니다.
6. 기획서에 동작이 없는 기능은 채우지 않고 공백으로 올립니다.
7. 다시 쓸 때는 지적받은 부분만 고치고 나머지는 그대로 둡니다.
8. 입력은 JSON 문자열로 주고, 출력은 JSON 하나로 받습니다. 그래도 파싱은 방어적으로 합니다(`llm.parse_json`은 코드펜스나 앞뒤 설명이 붙어 있어도 첫 JSON만 읽습니다).

## 프로토타입 범위

- 만든 것: 트리 생성과 검사(지어냄·누락·모양), leaf별 요구사항과 공백 분리, 계획, 작성, 규칙 검사, Judge, 공통 재생성 루프, TC 없는 AC 찾기, JSON/Markdown 리포트, 마크다운 트리 입력, 실행 흐름 기록(`trace.py`), 프롬프트 파일 분리(`prompts/*.md`). 테스트 59개가 이 흐름을 확인합니다.
- 안 만든 것: 실제 LLM 연결, 위키·디자인·이미지에서 기획서를 가져오는 부분, 위키·RAG 연동(아래 "뒤로 미룬 것").

## 뒤로 미룬 것

**LLM Wiki와 RAG는 이번 범위에서 빼고 [ROADMAP.md](ROADMAP.md)에만 적어 뒀습니다.** 이유는 세 가지입니다.

1. 이 구조의 효과(빠진 기능과 공백 찾기, 지어낸 수치 대조, 문제 있는 TC만 다시 쓰기)는 위키나 RAG 없이도 성립합니다. 둘은 효과를 더 키우는 확장이지 전제가 아닙니다.
2. 위키와 RAG는 트리의 leaf 경로를 키로 씁니다. 경로가 안정된 뒤에 붙이는 게 순서에 맞습니다.
3. RAG의 점수와 임계값은 측정부터 해야 합니다. 같은 기능의 TC는 유사도가 1.0 근처에 몰려 있어서, 측정 없이 임계값을 건드리면 달라야 할 TC까지 지울 수 있습니다.

나중에 붙일 수 있게 미리 만들어 둔 자리는 이렇습니다.

| 자리 | 위치 | 나중에 쓰이는 곳 |
|---|---|---|
| leaf 경로 `path`가 요구사항과 TC에 남음 | `models.py`, 결과 JSON | RAG의 범위 한정 검색, 서비스 단위 트리 |
| 프롬프트가 코드 밖 파일 | `prompts/*.md` | 위키 내용을 단계별 프롬프트에 끼워 넣을 때 |
| LLM은 `complete(system, user)` 하나만 앎 | `llm.py` | 단계별 모델 교체, 검색 결과를 user 입력에 추가 |

## 아직 정하지 못한 것

| 무엇 | 지금 상태 | 정할 때 볼 것 |
|---|---|---|
| 다시 만들기 한도(2회) | 근거 없이 정한 값입니다. 트리·AC·TC 모두 `gate.MAX_REVISIONS` 하나를 씁니다 | [EVALUATION.md](EVALUATION.md)의 재작성 결과로 측정 |
| 누락 판단이 애매하면 "누락"으로 답하게 한 것 | 놓치는 쪽 손해가 더 크다고 보고 정했습니다 | 오탐 때문에 트리를 괜히 다시 만드는 비율 |
| 트리를 다시 만들 때 통째로 새로 만들지, 지적된 부분만 고칠지 | 이전 트리와 피드백을 같이 주고 고치게 합니다. 모델이 전체를 바꿔 버릴 수도 있습니다 | 다시 만든 뒤 멀쩡하던 노드가 바뀌는 비율 |
| 직접 넣은 트리를 검사할지 | 검사하지 않습니다 | 사람이 만든 트리에도 누락·모양 검사가 도움이 되는지 |

## 기대 효과와 평가

사람이 검수해야 할 TC가 줄어드는 것을 기대합니다. 환각, 형식 위반, 분량 초과처럼 기계가 잡을 수 있는 문제는 사람에게 가기 전에 정리되니까, 사람은 FAIL, 공백, TC 없는 AC, 트리에 남은 문제만 보면 됩니다. 아직 실제 모델로 재 보지 않아서 수치로 말할 수는 없고, 아래 지표로 재 볼 계획입니다. 기준 세트를 만드는 법부터 지표별 계산 방법까지는 [EVALUATION.md](EVALUATION.md)에 있습니다.

| 지표 | 재는 방법 |
|---|---|
| 트리 정확도 | 사람이 만든 트리와 얼마나 맞는지, 원문 근거가 없는 노드의 비율 |
| 누락 탐지 | 사람이 찾은 빠진 기능 중 트리 검사가 잡은 비율, 누락이라고 잘못 짚은 비율 |
| 공백 탐지 | 사람이 찾은 기획서의 빈 곳 중 도구가 공백으로 올린 비율 |
| AC 커버리지 | 사람이 뽑은 AC 중 대응하는 TC가 있는 비율 |
| 환각률 | 기대결과 중 원문 근거가 없는 비율. 다시 쓰기를 켰을 때와 껐을 때 비교 |
| 검수 시간 | TC 100건을 사람이 검수하고 고치는 데 걸리는 시간. 다시 쓰기를 켰을 때와 껐을 때 비교 |
| 재작성 결과 | 한 번에 PASS한 비율, 끝내 FAIL로 남은 비율 |
| Judge 신뢰도 | 사람 판단과 맞는 비율 (세 항목 각각) |

## 한계

- 실제 모델로 돌려 본 적도 품질을 재 본 적도 없습니다. 테스트는 프롬프트마다 정해진 답을 주는 가짜 모델로 구조만 확인했습니다.
- 누락 검사는 문장 단위입니다. 한 노드의 인용이 긴 문장 하나를 통째로 덮으면 그 안에 든 두 번째 기능은 후보로 올라오지 않습니다. 제목 줄(`#`)에만 있는 기능도 못 봅니다. 마침표 없이 길게 이어지는 줄은 한 문장으로 칩니다.
- 누락 판단은 LLM이 하기 때문에 틀릴 수 있습니다. 트리를 만든 모델과 같은 계열이면 같은 착각을 할 수도 있습니다. 애매하면 누락으로 답하게 해서 오탐은 늘 수 있습니다.
- 코드는 빠진 기능을 직접 채우지 못합니다. 다시 만들기 한도를 넘겨도 누락이 남으면 리포트에 적을 뿐입니다.
- 원문을 그대로 복사하지 않고 살짝 바꿔 쓰면 진짜 기능도 지어낸 걸로 오인해서 잘라낼 수 있습니다. 프롬프트로 막고는 있지만 결국 모델에 달려 있습니다.
- 같은 기획서로 트리를 다시 만들면 모양이 달라질 수 있습니다. 서비스 단위로 트리를 쌓는 방식([ROADMAP.md](ROADMAP.md))이 이걸 줄여 줍니다.
- leaf마다 기획서 전문을 보내기 때문에 기획서가 길면 비용이 큽니다. leaf 주변만 잘라 보내면 줄일 수 있지만 아직 안 했습니다.
- 수치 대조는 숫자만 잡습니다. 없는 버튼 이름이나 없는 화면 전환은 Judge가 봐야 하는데, Judge도 같은 계열 모델이라 같은 착각을 할 수 있습니다.
- 원문에는 "삼십 분"처럼 한글로 적혀 있는데 AC나 기대결과에 "30분"이라고 쓰면 환각으로 잘못 잡을 수 있습니다.
