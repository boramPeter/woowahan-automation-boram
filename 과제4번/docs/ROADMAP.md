# 앞으로 할 일

여기 적은 건 전부 앞으로 하려는 것이고, 지금 코드에는 없습니다. 일부러 뒤로 미룬 것들입니다. 왜 미뤘는지, 나중에 붙일 수 있게 미리 만들어 둔 자리(leaf 경로 `path`, 코드 밖 프롬프트 파일)가 뭔지는 [DESIGN.md](DESIGN.md)의 "뒤로 미룬 것"에 있습니다. 기능분류트리로 요구사항을 뽑는 부분은 이미 구현돼 있어서([DESIGN.md](DESIGN.md)), 이 문서는 그 위에 얹을 것들만 다룹니다.

## 1. 지금 구조에서 약한 곳

| 약한 곳 | 왜 문제인가 | 이어서 할 일 |
|---|---|---|
| 같은 기획서로 트리를 다시 만들면 모양이 달라질 수 있음 | 과제끼리 비교하거나 회귀 범위를 잡기 어렵습니다 | 서비스 단위 트리를 위키에 쌓고, 새 기획서는 그 트리에 붙이기 (2절) |
| 트리의 누락 검사가 문장 단위라서 놓치는 게 있음 | 인용이 긴 문장 하나를 통째로 덮거나 제목 줄에만 있는 기능은 후보가 되지 않습니다 | 위키의 기존 트리와 비교해서 빠진 leaf 후보 찾기 |
| 기획서에 안 적힌 업무 규칙(권한, 상태 전이 등)을 모름 | AC가 얕아지고 공백이 너무 많이 나옵니다 | 도메인 지식을 위키에서 가져오기 |
| 같은 기능을 매번 처음부터 만듦 | 이미 있는 TC와 겹치고 비용도 듭니다 | 비슷한 요구사항·TC 검색 (3절) |
| leaf마다 기획서 전문을 보냄 | 기획서가 길면 비용이 큽니다 | leaf 주변 문단만 잘라서 보내기 |

## 2. LLM Wiki: 도메인 지식 쌓아 두기

도메인 지식을 정리해 두고, 단계마다 필요한 걸 꺼내 씁니다. 정리해 둘 내용은 이렇습니다.

- 용어집
- 정책·업무 규칙
- 서비스 단위 기능분류트리
- 시나리오 카탈로그 (도메인별로 자주 나오는 시나리오)
- 검사하면서 알게 된 규칙

붙는 자리는 이렇습니다.

| 위키 항목 | 붙는 단계 | 효과 |
|---|---|---|
| 서비스 단위 기능분류트리 | 트리 만들기 | 새 기획서가 기존 트리의 어디에 붙는지 판단합니다. 같은 기능이 매번 다른 이름으로 나오는 걸 막고, 빠진 leaf 후보도 찾을 수 있습니다 |
| 정책·업무 규칙 | 요구사항 뽑기 | 기획서에 안 적힌 전제를 채웁니다. 채운 부분은 출처를 "위키"로 표시해서 기획서 원문 근거와 섞이지 않게 합니다 |
| 용어집 | 트리 만들기, 작성 | 같은 개념을 같은 이름으로 씁니다. 개발 용어 대신 화면에 보이는 말로 씁니다 |
| 시나리오 카탈로그 | 계획 | 자주 나오는 시나리오를 후보로 줍니다. 필요 없는 건 계획 단계가 이유를 적고 뺍니다 |
| 검사하면서 알게 된 규칙 | TC 검사 | 자주 FAIL이 나는 패턴을 규칙 후보로 올립니다 |

위키는 자동으로 고치지 않습니다. 틀린 규칙이 한 번 들어가면 그 뒤에 만드는 모든 결과에 영향을 주기 때문에, LLM은 수정안만 만들고 사람이 승인해야 반영합니다.

## 3. RAG: 비슷한 요구사항·TC 가져오기

과거 요구사항과 TC를 쌓아 두고, 지금 만드는 것과 비슷한 것을 찾아오는 용도로만 씁니다. 쓰는 곳은 두 군데입니다.

- 계획 단계: 같은 기능의 과거 요구사항과 TC를 가져와서 시나리오 후보를 보강합니다. 트리가 있으니 먼저 leaf 경로로 범위를 좁히고, 그 안에서 유사도를 봅니다. 검색 범위가 좁아서 더 정확하고 비용도 적게 듭니다.
- 중복 점검: 새 TC가 이미 있는 TC와 같은지 봅니다.

쓰지 않는 곳도 정해 뒀습니다.

- TC 검사의 근거로는 쓰지 않습니다. 인용 대조와 수치 대조의 기준은 항상 이번 기획서 원문입니다. 과거 TC를 근거에 섞으면 옛 정책이 새 결과를 정당화해 버려서 환각을 잡을 수 없게 됩니다. 검색 결과는 프롬프트에 "참고용, 근거 아님"이라고 구분해서 넣습니다.
- 기대결과를 검색된 TC에서 그대로 가져오게 하지 않습니다. 기능이 바뀌었는데 옛 기대결과가 되살아납니다.

조심할 점이 있습니다. 과제가 달라도 같은 기능의 TC는 유사도가 아주 높은 쪽에 몰립니다. 임계값을 낮춰서 중복을 지우면 달라야 할 TC까지 지워집니다. 임계값을 만지기보다는 같은 기능은 최신본 하나만 남기는 쪽이 안전합니다. 그래서 적재할 때 leaf 경로, 과제 id, 날짜를 같이 저장해 둡니다.

## 4. 어디에 붙나

```
        ┌── LLM Wiki (용어 · 정책 · 서비스 트리 · 시나리오 카탈로그 · 검사 규칙) ──┐
        │                                                                  │
기획서 → 기능분류트리 → leaf별 요구사항 → 계획 ────→ 작성 ────→ 검사 → 다시 쓰기
                                          ▲
                                          └── RAG (비슷한 과거 요구사항·TC, 참고용)
```

## 5. 순서

1. 위키: 용어집과 시나리오 카탈로그부터 시작합니다. 처음엔 사람이 파일로 관리합니다.
2. 서비스 단위 트리: 과제마다 나온 트리를 위키에 쌓고, 다음 과제는 그 위에서 시작합니다.
3. RAG: 쌓는 것과 중복 점검을 먼저 하고, 그다음에 계획 단계의 참고 검색을 붙입니다.
4. 위키 자동 갱신 제안: 검사 결과에서 규칙 후보를 뽑아 올립니다.

앞 단계가 뒤 단계에서 쓰는 키(leaf 경로)를 안정시켜 주기 때문에 순서는 바꾸지 않는 게 좋습니다.

## 6. 그 밖에

- 입력 소스: 위키, 디자인, 이미지, 티켓 같은 새 소스는 기획서 텍스트로 합쳐서 넣거나, 트리를 직접 만들어 넣으면 됩니다.
- LLM: `LLMClient` 구현만 바꿔 끼우면 됩니다. 단계별로 다른 모델을 쓸 수도 있습니다(트리·계획·Judge는 큰 모델, 작성은 가벼운 모델).
- 규칙: `check_rules`에 패턴 한 줄과 테스트 하나를 더하면 됩니다.
- 출력: JSON, Markdown 말고도 스프레드시트나 테스트 관리 도구용 변환기를 붙일 수 있습니다.
- 병렬: 지금은 순서대로 돌립니다. leaf 단위, TC 단위 작업은 서로 독립이라 병렬로 돌릴 수 있습니다(동시에 부르는 수는 제한해야 합니다).
- 자동 실행: 티켓 이벤트로 돌리고 결과를 코멘트로 돌려줄 수 있습니다.
- 평가: 사람이 만든 트리와 라벨링한 기준 세트를 만들어 두면 트리 정확도, Judge 신뢰도, 모델을 바꿨을 때의 효과를 계속 재 볼 수 있습니다.
