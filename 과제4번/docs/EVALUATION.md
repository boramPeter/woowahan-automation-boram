# 평가 방법

[DESIGN.md](DESIGN.md)의 지표 표를 실제로 재는 절차입니다. **이 프로토타입은 아직 실제 모델로 돌려 본 적이 없어서 수치가 하나도 없습니다.** 이 문서는 수치를 얻는 방법만 적었고, 목표치는 일부러 적지 않았습니다. 첫 측정 전에 정한 목표치는 근거가 없기 때문입니다.

## 1. 먼저 준비할 것: 기준 세트

사람이 정답을 만들어 둔 입력 묶음입니다. 지표 대부분이 "사람이 정한 것과 비교"하는 방식이라 이게 없으면 잴 수 없습니다.

| 준비물 | 내용 | 쓰이는 지표 |
|---|---|---|
| 입력 | 기획서 원문 | 전부 |
| 정답 트리 | 마크다운 트리(`examples/sample_tree.md` 형식)로 사람이 직접 작성합니다. 기획서에 있는 기능이 전부 들어가야 합니다 | 트리 정확도, 누락 탐지 |
| 정답 공백 | "기능은 있는데 동작이 안 적힌" 곳의 목록 | 공백 탐지 |
| 정답 AC | 사람이 뽑은 leaf별 AC | AC 커버리지 |
| TC 라벨 | 도구가 만든 TC 한 건, 한 줄마다 사람이 매긴 판정 | 환각률, Judge 신뢰도 |

- 기획서는 도메인과 길이가 다른 것을 섞습니다. 몇 건이면 충분한지는 근거가 없으니, 처음엔 3~5건쯤으로 시작해서 지표가 얼마나 흔들리는지 보고 늘립니다.
- 정답을 한 사람이 만들면 그 사람의 기준이 곧 정답이 됩니다. 일부라도 두 사람이 따로 만들어서 서로 다른 곳을 보면 정답을 얼마나 믿을 수 있는지 알 수 있습니다.
- 사내 문서로 평가할 때는 허용된 모델 경로로만 돌리고, 기획서와 정답 세트를 이 저장소의 `examples/`에 넣지 않습니다. `examples/`는 가상 문서 전용입니다.

## 2. 돌리는 방법

1. 같은 입력을 **여러 번** 돌립니다. 모델 응답이 매번 달라서 한 번의 결과로는 우연인지 구분이 안 됩니다(처음엔 3회를 제안합니다).
2. 실행할 때마다 기록해 둡니다: 모델 이름, 설정, 프롬프트 파일의 해시(`shasum -a 256 tc_agent/prompts/*.md`), 입력 이름. 이 폴더는 git 저장소가 아니라서 해시가 프롬프트 버전을 알 수 있는 유일한 단서입니다.
3. 결과는 `report.to_json(result)`로 저장합니다. 아래 지표는 이 JSON의 `stats`, `requirements`, `test_cases`, `trace`, `gaps`, `pruned`, `tree_issues`에서 계산합니다.

**다시 만들기를 켰을 때와 껐을 때 비교.** `gate.MAX_REVISIONS = 0`으로 두면 다시 만들기가 꺼집니다. 검사는 그대로 돌기 때문에 문제 있는 TC는 바로 FAIL이 되고, 트리와 AC도 다시 만들지 않습니다(한도를 셋이 같이 쓰기 때문입니다). **검사 자체를 끄는 스위치는 지금 코드에 없습니다.** 그래서 "루프 없는 기준선"이라고 해도 실제로는 "다시 만들기를 끈 상태의 첫 결과물"입니다. 이 기준선에는 검사가 찾아낸 문제가 그대로 드러나지만, 검사가 놓친 문제는 두 조건 모두에 똑같이 남습니다.

## 3. 지표별 절차

### 3.1 트리 정확도와 누락 탐지 (②)

| 항목 | 계산 | 어디서 |
|---|---|---|
| leaf 정밀도 | 도구가 만든 leaf 중 정답 트리의 leaf와 맞는 것의 비율 | `tree`의 leaf와 정답 트리 비교 (맞는지는 사람이 판단) |
| leaf 재현율 | 정답 leaf 중 도구가 만든 것의 비율. 낮으면 빠진 기능이 남아 있다는 뜻입니다 | 위와 같음 |
| 근거 없는 노드 비율 | 잘라낸 노드 ÷ (남은 leaf + 잘라낸 노드), 대략값 | `stats.pruned_nodes`, `stats.leaves` |
| 모델이 한 번에 통과한 비율 | 다시 만들지 않고 첫 트리가 검사를 통과한 실행의 비율 | `trace`에 "회차 재생성"이 없는 실행 |

누락 검사는 따로 잽니다. 정답 트리에는 있는데 도구의 최종 트리에는 없는 기능을 "빠진 기능"으로 보고 아래처럼 셉니다.

| 항목 | 계산 | 어디서 |
|---|---|---|
| 누락 탐지율 | 빠진 기능 중 ②가 한 번이라도 누락으로 짚은 비율 | `trace`의 `[major/omission]` 메시지와 정답 비교 |
| 누락 오탐률 | 누락이라고 짚었는데 사람이 보니 이미 노드가 있거나 기능이 아닌 비율 | 위와 같음 |
| 짚은 뒤 해결된 비율 | 누락이라고 짚은 뒤 다시 만든 트리에서 실제로 채워진 비율 | 짚기 전후의 트리 비교 |
| 끝내 남은 누락 | 다시 만들기 한도를 넘겨도 남은 누락 | `tree_issues`의 `omission` |
| 판단 못 한 비율 | `omission_check_error`가 난 실행의 비율. 이 실행의 트리는 누락 검사를 사실상 거치지 않은 셈입니다 | `tree_issues` |

한계: 누락 후보는 "어느 노드의 인용에도 안 걸린 문장"이라서, 인용이 긴 문장 하나를 통째로 덮은 경우나 제목 줄에만 있는 기능은 후보가 되지 않습니다. 이런 누락은 정답 트리와 비교해야만 보이니까 위의 leaf 재현율을 같이 봅니다.

### 3.2 공백 탐지

- **재현율:** 정답 공백 중 도구가 `gaps`에 올린 비율.
- **정밀도:** `gaps` 중 사람이 봐도 진짜 공백인 비율.
- **놓친 공백:** 정답 공백인데 도구가 AC를 지어낸 경우. 3.4의 환각으로도 잡히는지 같이 봅니다.

### 3.3 AC 커버리지

두 가지가 서로 다릅니다. 섞어서 말하지 않습니다.

| 이름 | 계산 | 무엇을 보나 |
|---|---|---|
| 도구 기준 커버리지 | 1 − `stats.uncovered_acs` ÷ 전체 AC (`requirements[].acs`의 길이 합) | 도구가 **뽑은** AC를 TC가 다뤘는가 (계획 단계에서 빠뜨렸는지) |
| 사람 기준 AC 재현율 | 정답 AC 중 도구의 AC가 담고 있는 비율 | AC를 **뽑는 단계**에서 빠뜨렸는지 |
| 사람 기준 TC 대응률 | 정답 AC 중 대응하는 TC가 있는 비율 | 둘을 합친 최종 결과 |

도구 기준 수치는 AC를 뽑다가 빠뜨린 것을 볼 수 없어서 높게 나오기 쉽습니다. 최종 판단은 사람 기준으로 합니다.

### 3.4 환각률

**정의:** 기대결과 한 줄마다 사람이 원문과 대조해서 "근거 있음 / 없음"을 매깁니다. 환각률 = 근거 없는 줄 ÷ 기대결과 전체 줄.

두 대상을 따로 셉니다.

| 대상 | 뜻 |
|---|---|
| 최종 PASS TC | 사람에게 실제로 전달되는 것의 환각률 |
| 다시 쓰기를 끈 첫 작성본 | 검사를 받기 전, 모델이 처음 쓴 그대로의 환각률 |

그리고 가장 중요한 지표가 하나 더 있습니다.

- **검사가 놓친 비율:** 사람이 환각이라고 판단한 TC 중 도구가 PASS로 통과시킨 비율. 규칙은 **수치**만 대조하기 때문에, 없는 버튼 이름이나 없는 화면 전환은 규칙을 그냥 지나가고, 같은 계열 모델인 Judge도 같은 착각을 할 수 있습니다. 이 수치가 높으면 "사람은 FAIL만 보면 된다"는 설계의 전제가 깨집니다.

### 3.5 검수 시간

TC 100건을 사람이 검수하고 고치는 시간을 두 방식으로 잽니다.

| 방식 | 검수 대상 |
|---|---|
| 전수 검수 | 모든 TC |
| 도구 사용 | FAIL, 공백, TC 없는 AC, 비고가 있는 TC만 |

- 같은 사람이 같은 기획서를 두 번 보면 익숙해져서 시간이 줄어듭니다. 기획서를 나누고, 사람마다 조건을 엇갈리게 배정합니다.
- "도구 사용" 방식은 시간이 줄어도 3.4에서 말한 놓친 문제가 있으면 품질이 떨어진 대가일 수 있습니다. 시간과 함께 검수자가 놓친 문제 수도 기록합니다.

### 3.6 재작성 결과

`test_cases[]`의 `status`와 `revisions`로 계산합니다.

| 항목 | 계산 |
|---|---|
| 한 번에 PASS | `revisions == 0`이고 `PASS`인 TC ÷ 전체 |
| 다시 쓰고 PASS | `revisions ≥ 1`이고 `PASS`인 TC ÷ 전체 |
| 끝내 FAIL | `FAIL`인 TC ÷ 전체 |
| 자주 걸리는 규칙 | `trace`의 검사 메시지에서 `[major/<규칙>]`을 집계 |

다시 만들기 한도(`gate.MAX_REVISIONS`, 2회, 트리·AC·TC 공통)는 근거 없이 정한 값입니다. "다시 쓰고 PASS" 중에서 1회차와 2회차 비율을 보면 한도를 늘릴 만한지 알 수 있습니다. 트리도 같은 방식으로, 첫 트리가 통과한 비율과 1회차·2회차에 통과한 비율을 `trace`에서 셉니다.

### 3.7 Judge 신뢰도

Judge는 **규칙을 통과한 TC만** 봅니다. 사람 판단과 비교할 표본은 PASS와 FAIL을 섞어서 뽑습니다.

| 항목 | 계산 |
|---|---|
| 일치율 | 정확성·완결성·명확성 각각, 사람 판단과 Judge 판단이 같은 비율 |
| FAIL 정밀도 / 재현율 | Judge가 FAIL로 본 것 중 사람도 FAIL인 비율 / 사람이 FAIL로 본 것 중 Judge도 FAIL인 비율 |
| 판단 못 한 비율 | 비고에 `judge_error`가 있는 TC ÷ Judge가 본 TC |

- **`judge_error`는 minor라서 PASS로 통과합니다.** Judge 응답이 깨진 TC는 사실상 Judge를 거치지 않았는데도 PASS로 집계됩니다. 이 비율이 높으면 PASS 수치를 그대로 믿으면 안 됩니다.
- Judge가 FAIL로 본 이유는 다시 쓰기 전의 작성본까지 포함해서 `trace`의 검사 메시지에 남습니다. PASS인 TC의 항목별 판단은 따로 저장되지 않고, "세 항목 모두 PASS"라는 것만 알 수 있습니다.

## 4. 결과 기록 양식

실행할 때마다 한 줄씩 채웁니다. 아직 숫자가 없으니 비워 둡니다.

| 입력 | 모델 | 프롬프트 해시 | 다시 만들기 한도 | 트리 leaf 재현율 | 누락 탐지율 | 한 번에 PASS | 다시 쓰고 PASS | FAIL | 환각률(최종) | 검사가 놓친 비율 | `judge_error` |
|---|---|---|---|---|---|---|---|---|---|---|---|
| | | | | | | | | | | | |

## 5. 이 평가로 알 수 없는 것

- 사람이 만든 TC와 견줘서 **전체적으로 더 좋은지 나쁜지**는 보지 않습니다. 환각, 형식, 커버리지 같은 개별 결함만 잽니다.
- 기준 세트가 소수의 문서라서 다른 도메인에서도 같은 수치가 나온다는 보장이 없습니다.
- 프롬프트를 바꾸면 모든 수치가 달라집니다. 비교는 같은 기준 세트, 같은 모델, 같은 프롬프트 해시로 돌린 실행끼리만 합니다.
